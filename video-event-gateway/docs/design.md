# 工程设计与演进

## 当前数据路径

`veg_gateway` 读取一份 YAML，给每个源启动一个 C++ 工作线程。各线程独立拉流、重连、检测、目标关联、执行规则和存证。公共 HTTP 服务汇总每路状态、近期事件和指标。RTSP 测试服务器是另一个独立进程；真实摄像头可以直接替换输入 URL。

```text
RTSP / 文件 ── VideoCapture ── 检测 ── 跟踪 ── 规则 ── JSONL + PNG
                                       │          │
                                       └── 状态 ──┴── Drogon API
```

`veg_detect` 是单路命令行版本，其采集和处理使用两个线程及容量为三帧的队列。实时输入在队列满时丢弃最旧帧，文件回放等待消费者，保证结果可复现。`veg_gateway` 目前每路采集与处理串行，输入侧暂时依靠解码器缓冲；增加多路高帧率 AI 输入时，应补上有界队列、按时钟丢帧和检测帧率配置。

## 模块职责

- OpenCV：视频解码接口、背景差分、图像处理及证据截图。
- ncnn：可选 YOLOv8 人员检测；边界是 `std::vector<cv::Rect>`，后续可实现 RKNN 检测器并复用规则。
- `veg::VideoEventProcessor`：根据检测框更新简单轨迹，输出越线、区域进入和滞留事件。
- Drogon：只读的状态、近期事件与指标接口。
- GStreamer RTSP Server：开发阶段的测试录像发布，不参与真实摄像头拉流处理。

事件同时包含 `camera_id`、`track_id`、帧序号、视频时间戳、事件生成的 Unix 时间、检测框与截图路径。每条轨迹对同一规则只触发一次。`dwell_frames` 以处理帧计数；处理帧率变化时对应的真实时间也会变化，因此正式业务规则应该进一步改为时间阈值。

文件帧优先使用视频时间戳，缺失时按帧率估算；RTSP 使用本次连接开始后的单调时间。当前时间戳不能跨重连连续对齐到摄像头原始时钟，后续需要明确定义统一时钟和延迟指标。

## 已验证与尚未验证

在 Ubuntu 虚拟机中，CTest 已验证：

1. 越线、区域进入与滞留规则；
2. 合成录像的单路处理；
3. H.264 RTSP 发布与接收回环；
4. 两路并发 RTSP 输入、各 120 帧、API 查询、指标与截图；
5. ncnn 对人物样例的检测、12 帧事件处理与截图。

人物样例是由单张照片生成的短视频，仅验证整条代码路径。没有真实视频行为识别的精度数据。运动检测对光照、阴影与动态背景敏感；简单目标关联在遮挡或目标交叉时会换 ID。当前 HTTP 接口无认证，事件查询只保留内存中最近 200 条；JSONL 没有轮转，PNG 没有保留期。工作线程的单次 `VideoCapture` 打开/读取调用也可能受底层后端阻塞。以上均需在长期运行前处理。

`scripts/benchmark_gateway.py` 可以对有限帧回放查询 `/health`，并从 `/proc/<pid>/status` 读取进程的 `VmHWM`。Ubuntu VM 中单路 832×416 人物样例、12 帧 CPU ncnn 回放的峰值 RSS 约 168 MiB、平均每帧处理约 64 ms。此值包含网关及其依赖的驻留内存，不含另一个 RTSP 发布进程，也不代表多路、长时间运行或目标硬件性能。

## 下一阶段里程碑

1. **真实视频基线**：提供经过授权的测试视频或摄像头 RTSP，标注明确的违规行为定义和样本。记录误报、漏报、端到端延迟。
2. **可靠采集**：引入采集与处理有界队列、超时与重连测试，按摄像头时钟计算事件时间，限制推理采样率。
3. **目标跟踪**：以更稳健的关联器替换质心贪心匹配，量化遮挡场景中的 ID 切换。
4. **业务模型**：根据选择的违规场景接入检测、姿态或时序模型；把类别和规则分开配置。安全帽与跌倒不是同一种模型任务。
5. **服务化**：事件日志轮转、截图配额、优雅退出、鉴权、健康检查语义和长期压力测试。
6. **RK3588**：先跑 CPU 基线，再接硬件解码和 RKNN 推理，测 1/2/4 路的峰值 RSS、CPU/NPU 占用、丢帧及 P95 延迟；按测量结果调整模型、分辨率与路数。
