# RK3588S 多协议智能视频网关：实施规划

## 项目定位

面向嵌入式 Linux / C++ 岗位，做一个能在 Orange Pi 5 Pro（RK3588S、16 GiB）长期运行的智能视频网关。它从 CSI 摄像头获取画面，发布 RTSP 和 RTMP 流；独立的 AI 支路识别人员并产生越线、区域进入和滞留事件。浏览器预览、告警查询和运行指标构成可演示的完整链路。

这不是从零重写 RTSP/RTMP 协议栈。成熟的媒体服务器承担协议处理；本仓库的 C++ 代码负责设备接入、生命周期、帧队列、推理、规则、事件与运维集成。简历中明确说明第三方组件和自己实现的边界。

## 2026-11-14 实机基线

合成流 RTSP/RTMP 回环和独立用户服务已完成，实测见[板端流媒体基线](streaming_board_smoke.md)。摄像头出图、硬件加速、AI 和长期运行仍是待办。

通过 `ssh orangepi@192.168.1.101` 做了只读检查：

| 项目 | 观察结果 | 结论 |
| --- | --- | --- |
| 系统 | Orange Pi 1.0.8 Resolute / Ubuntu 26.04，内核 `6.18.49-rockchip-rk3588` | 现有音频环境先保留，不直接替换系统 |
| 资源 | 约 15 GiB 内存、根分区 57 GiB（可用约 48 GiB） | 模型、构建缓存和录像应限制体积 |
| 摄像头 | 用户确认是 CSI 排线连接；`v4l2-ctl --list-devices` 只列出 RGA、解码器和编码器，未列出 CSI/ISP 采集设备 | 第一关是确认传感器型号、驱动、设备树和实际出图 |
| 编码 | 内核出现 `rk3588-vepu121-enc`，FFmpeg 枚举 `h264_v4l2m2m` | 仅说明接口存在，硬件编码可用性、格式和性能尚未实测 |
| NPU | 系统有 `librknnrt.so`，未见 `/dev/rknpu*` | RKNN 推理链路尚未验收，不能据此宣称 NPU 已可用 |
| 散热 | 此前音频长负载观察到约 89°C；用户当时确认未装散热 | 连续视频推理及 24 小时压测前需解决散热并记录温度 |

当前启动配置没有摄像头 overlay。摄像头模块型号、接入的 CAM 口和排线方向尚待确认。现有内核配置中未看到 RKISP/RKCIF 采集驱动，因此不能假定仅修改 `/boot/orangepiEnv.txt` 就能出图。先在现有系统做只读诊断；如果必须使用厂商 BSP 内核，应在独立启动介质上验证并保留当前系统的回退路径。

## 技术选择

| 组件 | 用法与取舍 |
| --- | --- |
| [ZLMediaKit](https://github.com/ZLMediaKit/ZLMediaKit) | 首选 C++ 媒体服务器，接收发布流、对外提供 RTSP/RTMP，并可按需提供 HLS/WebRTC。通过其 HTTP API 和 hook 与本项目对接；锁定具体提交或版本，不直接复制源码。 |
| [SRS](https://github.com/ossrs/srs) | 作为 RTMP/WebRTC 方案对照和协议压测参考。此阶段不同时部署两套生产媒体服务器。 |
| [MediaMTX](https://github.com/bluenviron/mediamtx) | 轻量协议回环与故障对照工具；它是 Go 项目，不作为本项目的 C++ 代码主体。 |
| [RKNN Model Zoo](https://github.com/airockchip/rknn_model_zoo) / [RKNN-Toolkit2](https://github.com/airockchip/rknn-toolkit2) | 从官方 YOLOv8n 人员检测示例开始，在 Ubuntu 主机转换模型，板端使用 C/C++ runtime；先验证运行时与驱动兼容。模型权重不入库。 |
| [Rockchip MPP](https://github.com/rockchip-linux/mpp) | 硬件编解码的候选实现。只有在当前系统实测可用时才接入；保留软件编码作为功能基线。 |

保留现有 `veg_rtsp_server` 作为小型测试发布端，继续用于离线回归；对外服务由 ZLMediaKit 承担。初版统一使用 H.264 视频，音频存在时再验证 AAC，避免不同客户端对 H.265/RTMP 的兼容性差异。

## 目标架构

```text
CSI 摄像头 ── 采集 / 色彩转换 ── H.264 编码 ── ZLMediaKit ── RTSP / RTMP 客户端
                  │                                  │
                  └── 有界抽帧队列 ── RKNN YOLOv8n ── 跟踪 / 规则 ── 事件 API
                                             │
                                             └── 可选标注流（后续阶段，需重新编码）

Windows 主机：接收事件、低频状态和必要日志 → E:\orange Pi 5 Pro\log
```

媒体转发与 AI 支路解耦：AI 变慢时丢弃过期分析帧并统计丢帧，不让 RTSP/RTMP 播放堆积。若将来接入已经编码的网络摄像头，优先直接转封装原始流，只给 AI 支路解码抽帧。标注后的画面另发一路流，避免破坏原始流。

## 阶段与验收

| 阶段 | 本仓库要完成的工作 | 验收证据 |
| --- | --- | --- |
| 0. CSI 出图 | 确认传感器型号和 CAM 口；核对设备树、驱动和 media graph；用 `v4l2-ctl`/GStreamer 抓取原始帧。若当前镜像不支持，在独立介质验证合适的板卡镜像。 | 记录分辨率、像素格式、实际帧率、连续采集 10 分钟结果与可复现命令。 |
| 1. RTSP/RTMP 最小闭环 | 部署固定版本 ZLMediaKit；C++ 采集发布器提供摄像头画面；从另一台设备分别用 RTSP 和 RTMP 拉流；加入断流重连。 | 两种协议都能连续播放；抓取连接建立时间、丢帧/重连次数；摄像头断开与恢复可见。 |
| 2. C++ 控制平面 | 把现有 `veg_gateway` 拆成采集、发布、AI 和事件模块；配置校验、服务状态机、健康接口、Prometheus 指标、受控的队列和退出处理。 | 单元测试、虚拟机回环测试、板端重启/断线恢复测试。 |
| 3. RKNN AI 支路 | 先接 YOLOv8n 人员检测，再用现有越线/区域/滞留规则生成事件；保留 CPU 后端作为对照。 | 标注数据上的精确率、召回率、误报数；板端推理延迟、分析 FPS、NPU/CPU 占用。人物检测不冒称“违规动作识别”。 |
| 4. 性能与长期运行 | 实测硬件编码/解码，必要时用 MPP/RGA 优化；做 24 小时运行、客户端并发、断网/摄像头故障注入和热稳定性测试。 | P50/P95 播放延迟、端到端事件延迟、温度、RSS、磁盘、丢帧、重连次数和恢复时间。 |
| 5. 求职展示 | 完整 README、架构图、演示视频、构建/部署脚本、测试报告与故障记录。 | 从干净环境复现；展示 RTSP/RTMP 拉流、事件触发和监控面板。 |

首个可展示版本只要求 **1 路 CSI 摄像头 + RTSP/RTMP 双协议 + 人员越线事件**。之后再扩展多路、WebRTC、标注流和更复杂的违规行为。每次扩展都先测真实板端指标，不预先承诺可处理路数或 NPU FPS。

## 工程约束

- 新代码以 C++17/CMake 为主，Python 限于模型转换、评测和自动化测试。第三方依赖锁定版本并保留许可证说明。
- 本项目不改动 Zynq/PetaLinux 环境。板端优先使用独立工作目录和可回退的 systemd 服务。
- 模型、构建产物、录像与高频日志不提交 Git；板端不持久保存测试录像或运行日志。必要事件与状态由有界内存队列转发到 Windows 的 `E:\orange Pi 5 Pro\log`，主机离线时不无限积压。
- RTSP/RTMP 管理接口先限制在受控局域网，发布/播放凭据不写入仓库；对外暴露前补鉴权和传输保护。
