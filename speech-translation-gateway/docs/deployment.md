# AI 语音部署流程与后续优化

## 从模型到可用服务

| 阶段 | 要做的事 | 本阶段状态 |
| --- | --- | --- |
| 需求与预算 | 确定语言、离线要求、音频来源、延迟目标、并发数和内存上限 | 先按单路、离线、中文与英文、Ubuntu CPU 建立基线 |
| 模型筛选 | 比较准确率、合成效果、模型大小、许可证和运行时支持 | SenseVoice INT8；Kokoro INT8、Piper 中英；Silero VAD |
| 固定版本 | 固定运行时和模型版本，校验下载哈希，记录配置 | `install_vm_models.sh` 固定运行时版本及归档 SHA-256 |
| 信号预处理 | 解码、单声道、采样率转换、音量与静音检查、VAD 分段 | C++ 接受 WAV；启用 VAD 时将输入重采样到 16 kHz |
| 推理集成 | 加载模型、设置线程、预热、处理请求、输出结果 | C++ CLI 调用 sherpa-onnx C API；模型在一次命令内常驻 |
| 正确性验证 | 有参考文本的 CER/WER、静音误触发、噪声、TTS 回读 | 公开双语录音、固定噪声、静音、合成回读；样本量很小 |
| 性能测量 | 加载时间、推理均值和尾延迟、实时率、峰值内存 | JSON 报告及 1/2/4 线程对比 |
| 交付运维 | 长驻服务、请求队列、并发、监控、恢复、部署包 | 本机 C++ HTTP 服务、systemd 自动重启、健康检查、限流和短期压力测试已完成；持续运行验收仍需更长观察 |

## C++ 能承担什么

C++ 可以完成实时音频采集、解码与重采样、VAD、模型推理、结果后处理、线程池、长驻服务、指标记录和跨平台部署。本项目已用 C++ 完成 WAV 路径上的 VAD、STT、TTS、重采样和计时。当前 Python 脚本只做离线评测。

并非所有步骤都适合只用 C++：模型训练、导出、量化校准和 RKNN 转换通常依赖模型提供者的 Python 工具链。转换得到的模型仍可在板端经 C/C++ Runtime 调用。RK3588 的 NPU 能否运行某个模型，取决于算子、模型格式、RKNN 工具链版本和实测结果；不能把 ONNX 在虚拟机上能运行等同于 NPU 可用。[RKNN Toolkit2 官方仓库](https://github.com/airockchip/rknn-toolkit2) 与 [sherpa-onnx RKNN 模型列表](https://k2-fsa.github.io/sherpa/onnx/rknn/models.html) 是迁移时的起点。

## 指标口径

- **模型加载时间**：从创建运行时实例到返回；当前每次 CLI 启动都会付出该成本。将来长驻服务应在启动时加载一次。
- **推理延迟**：完成指定预热后，单次 STT 解码或 TTS 合成的耗时；报告均值、P50、P95。当前 P95 仅由 3～7 次重复估算，不具备稳定的尾延迟统计意义。
- **RTF（实时率）**：推理秒数 ÷ 输入音频时长（STT）或生成音频时长（TTS）。小于 1 表示处理速度快于播放速度。RTF 不含模型加载、WAV 读写、VAD 与队列等待。
- **峰值 RSS**：单个进程运行期间的最高常驻内存，含模型、运行时及中间缓存；不是板端内存预算的完整测量。
- **CER/WER**：中文字符错误率和英文词错误率，均为最小编辑次数 ÷ 参考字符或词数。评测脚本做了大小写、标点和全半角归一化，并将中文“九/五”与 `9/5` 视为等价。该规则只为这批样本服务。
- **噪声鲁棒性**：以固定随机种子加入 20/10 dB SNR 高斯噪声，比较 CER/WER。仍需真实环境录音才能判断产品效果。
- **TTS 信号检查**：生成音频的采样率、时长、RMS 电平、削波比例，以及经另一个 STT 模型回读的文本。回读相同不代表声音自然、无伪影或口音合适。
- **静音误触发**：输入 1 秒全零波形，核验 VAD 是否阻止无声转写。带 VAD 时零语音片段的 STT 推理时间为 0；仍需计入 VAD 和加载时间。

当前 `vad_ms` 只计 VAD 推进和切段，不包括前面的重采样；命令返回的 `inference_*` 不包含音频读写、VAD 或模型加载。正式服务需要额外测量从请求到响应的端到端 P95/P99、吞吐量、并发时内存和 CPU 使用率。

## 已做的优化与下一轮实验

1. **INT8 权重**：SenseVoice 和 Kokoro 采用上游提供的 INT8 版本；Piper 采用上游 medium 模型。不能将它们的速度差全部归因于量化，因为网络结构也不同。
2. **CPU 线程扫描**：在 VM 的 4 个 vCPU 上测 1/2/4 线程，避免凭经验选线程数；单请求结果见 `results.md`。并发多请求时需重新调优，总线程数过多可能降低吞吐。
3. **VAD**：跳过静音的 STT 解码，并让较长录音分段。它修复了这批纯静音输入的误触发，但可能影响弱语音和噪声样本，阈值需要真实数据调整。
4. **模型选择**：在相同短句上实测 Piper 与 Kokoro 的延迟、RSS 和回读。默认先以 Piper 做低延迟路线，Kokoro 保留作音色对照；音质尚未听测。
5. **常驻服务**：现有 `speech_server` 在启动时加载模型，通过本机 HTTP 接口复用；请求限流和 systemd 故障重启已验证。服务 P95 是完整请求耗时，不能与 CLI 的纯模型推理时间直接比较。
6. **下一轮**：实际麦克风/电话带宽语音、真实业务标注语料、持续并发、文本切句和流式输出。语音翻译还须接入翻译模型，单独测译文质量及整条链路的 P95。

## RK3588 迁移检查

8 GiB DDR 对当前几个模型的容量看起来充裕，但不能仅按 `.onnx` 文件大小估算：运行时、声学缓存、并发请求、操作系统和视频管线都会占用内存。迁移时先确认 OS、aarch64 ABI、运行时动态库及板端音频设备；以 CPU 版本复现功能；再尝试有官方支持的 RKNN 模型与 NPU Runtime。对每一项量化或 NPU 替换，必须比较同一批样本的输出、延迟、峰值 RSS 与功耗。不要把 x86 虚拟机结果当成 RK3588 的性能预测。
